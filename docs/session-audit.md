# Session audit

Why: an imported account keeps working only while nobody else holds a session of it. Whoever does can end ours (terminate all other sessions) or kept a copy of the auth key. Telebuba never ends other sessions by itself; the audit shows who is there.

## What it reads

`account.getAuthorizations`, from each of the account's own pooled clients (desktop and/or mobile, each its own authorization). Telegram marks only the session that asked as `current`, and lists it with `hash=0`; every other entry carries its real, stable hash, the same from every viewer. So the `current` entry is OURS, and another device of ours is found by difference: its real hash is the one entry the primary lists that the device itself does not list besides itself. If that is not exactly one entry, the read fails. `0` is never a key of any other entry, and is never closed. What a session looks like decides nothing: an imported seller session wears the seller's own device by design, so a look-alike is exactly the case a heuristic would hide.

If any one of the account's clients cannot answer, the whole read fails: a partial answer would list our own second session as foreign, and closing "foreign" sessions would then end it.

The one exception is a non-primary device whose key Telegram has provably ended (the explicit dead-key errors, `AUTH_KEY_UNREGISTERED`, `SESSION_REVOKED`, `AUTH_KEY_DUPLICATED` and kin; not a network error, a timeout or a failed `is_user_authorized`, which prove nothing): it has no authorization left to list, so it is treated as absent. The read goes on with the other device(s), the result names the dead device, and the audit logs `session_audit_device_dead` (device type only). This keeps a dead second device from blocking every close, the seller-known old key's included. A dead primary is still `session_dead`.

The Telegram app inside a mobile container (pod) is not one of our clients, so its authorization is not recognised as ours and lists as foreign. Closing is therefore always an explicit, confirmed operator action.

**Marked ours by hand.** What Telebuba cannot prove (an orphan of a failed sign-in, a login made by hand, a web login from before they were recorded) the operator can mark as ours on the card ("This session is ours", `PUT /accounts/{id}/sessions/{hash}/ours`); it then counts as ours (kind `manual`): no foreign badge, no alert, and a close refuses it. Nothing is closed and Telegram is not asked. Only such a mark can be taken back.

**Our web window's login is ours from the moment it is accepted.** When WebK's QR token is accepted with the account's pooled client, Telegram names the new authorization. If it is flagged unconfirmed, Telebuba answers the "is this you?" question with `account.changeAuthorizationSettings(confirmed=True)` (best effort; a failure is logged and never fails the login). The hash is written to `account_own_authorizations` (kind `web`) right then, before anything else touches the window (`own_web_authorizations_recorded`, `at: acceptance`), so a restart or a failed listing cannot leave the browser's login shown as foreign. The later background recorder only refreshes the saved snapshot.

**A web window never outlives its proxy or its account.** Assigning, re-assigning, unassigning or removing a proxy closes the window of every affected account (`account_web_window_closed`, `reason: proxy_changed`); it waits at most 2 s for a login in progress to release the open lock, then ends the window anyway. Deleting an account first drops a tombstone file (`.telebuba-remove`) into its browser profile, then removes the profile; if the removal fails, the startup sweep (`remove_orphaned_web_profiles`) removes exactly the profiles that carry a tombstone and have no open window. It never decides from the database: an empty or restored database must not match every profile.

## When it runs

- On demand from the account's "Sessions" card.
- Once, right after the first `alive` session check of an account that has a proxy. Like the 2FA record it needs a proxy: the import flow stays offline, because a proxyless client connects from the operator's own IP.

## What is kept

- `account_session_audits`: the latest snapshot per account (it names other people's IP and device, so it is deleted with the account).
- `account_session_audit_events`: one row per audit (`checked_at`, `total`, `foreign_count`, `killed_count`), counts only.
- The lifecycle journal gets `foreign_sessions_found` when a foreign session shows up that the previous audit did not list, with counts only, and a `session_dead` row carries `last_audit_at` / `last_audit_total` / `last_audit_foreign`, so a death can be bracketed ("the last audit saw N sessions at T").

No log line, journal row or API error carries a session hash, IP or device.

## Closing foreign sessions

An explicit operator action: the card's "Close foreign sessions" (a confirm dialog lists exactly what will go), and a "Sessions" tab in the bulk editor for several accounts.

- **Refused while a sign-in is in flight.** Every sign-in or sign-out of the account (second device, QR, phone code, passkey, re-key, logout, removal) holds the account's auth lock, and the session it creates is listed as foreign until it is recorded. While that lock is held a close is refused with `sign_in_in_progress` before any Telegram call, and the lock is only looked at, never awaited (a QR sign-in holds it for minutes). The audit read itself is refused the same way, so a session of ours that appears mid-sign-in neither raises a "new foreign session" alert nor is saved as foreign; nothing is lost, because a read after the sign-in sees a really foreign session as news. The re-key's own old-key close does not go through this check: it runs after the re-key released its lock.
- **"Close all foreign" closes only what the operator was shown.** The set is the intersection of the saved audit's foreign sessions (the card) and what Telegram lists now. A foreign session that first appears in this run's read is saved (the card shows it) but not closed: the result counts it (`unseen_count`). With no saved audit nothing was shown, so one is read and saved, nothing is closed, and the result says so (`no_prior_audit`). A close by named hashes keeps its semantics.
- One `account.resetAuthorization` per session, **never** `auth.resetAuthorizations`: an account can hold a second sign-in of its own, and that call would end it.
- The list is read again first. A hash that is no longer listed is already gone; one that is ours is refused whatever was asked. This also covers a session the operator confirmed that turned out to be ours.
- Telegram refuses the call from a session younger than 24 hours (`FRESH_RESET_AUTHORISATION_FORBIDDEN`, [account.resetAuthorization](https://core.telegram.org/method/account.resetAuthorization)). The imported seller session is old, so it can. That refusal ends the run and is reported as `too_new` with the time left, not as an error. A flood wait does the same.
- The calls are paced: the service draws a human-like pause for every gap (`SESSION_AUDIT__CLOSE_PAUSE_*`); core holds no randomness.
- Afterwards the account is audited again, so the screen shows what Telegram lists. The count is kept in the audit history (`killed_count`) and journalled (`foreign_sessions_closed`, counts only).
- The Telegram app inside a mobile container is not recognised as ours, so it lists as foreign and would be closed too if the operator confirms it.

## Re-key: a login the seller never had a copy of

An imported `.session` shares its auth key with whoever kept a copy. "Re-key the session" (card, and a bulk tab; never automatic) signs the account in again as a session of its own:

1. A new client with its own scratch session file (the account's stored device fingerprint and proxy, so Telegram sees the same device) calls `auth.exportLoginToken`; the imported session calls `auth.acceptLoginToken` with that token. If the new authorization comes back flagged `unconfirmed`, the imported session confirms it (`account.changeAuthorizationSettings`).
2. If the account has a cloud password, the new login finishes with the stored one (`SESSION_PASSWORD_NEEDED` after the token is accepted); without it the re-key is refused (`rekey_twofa_missing`) and nothing changed. The password is only passed to Telegram.
3. The new session must be the same Telegram user. Then the files are swapped: the imported file is set aside (not deleted), the new one is opened once from its final place and must answer as the same user, and only then is the imported file deleted. Any failure before that answer puts the imported file back and ends the new authorization. Once the new file has answered, the swap is done: a side file that cannot be deleted afterwards (another process holding it, on Windows) is only logged, because undoing then would end the key the account's file now holds. The undo never ends the new authorization while the account's file may hold its key (it compares the keys), and a copy-back that fails ends nothing: the side copy (`.rekey-aside`) is kept, the row records `rekey_incomplete`, and no new re-key starts while a side copy holds a key the account's file does not.
3a. The imported session cannot name its own key (it sees itself as `0`), so the old hash is read from the NEW session after it signed in and before the swap: the one non-zero hash it lists that the imported session's list (read before the token) did not contain, and, when the imported session's entry has a creation date, one created at that time. Zero or several candidates, or a date mismatch, refuse the re-key with `rekey_old_key_unknown` through the normal failure path: the new login is ended and the imported session stays.
4. The old authorization (the seller-known key) is ended by the operator from the card ("Close the old session"), after a checklist: SpamBot clean with no limit in the last month, the new session at least a week old, a second device of ours where a login code could arrive (a Telegram Web login does not count: Telegram has been seen ending ours within a day or two), and a 2FA password Telegram accepted plus a passkey whose vault key answers as present (the seller's unverified password does not count; a sealed or unreachable vault is not ok; no Telegram call is made). The items only inform; the operator decides. This is the default because on 2026-11-14 an account's new key died about a second after Telebuba ended its 2.5-month-old official Telegram Desktop session from the six-day-old unofficial one, on an account SpamBot had limited: to Telegram that looks like an account takeover. The close uses the same single-hash call as "close foreign sessions"; a refusal (a young session cannot end others) comes back as the time to try again. With `SESSION_AUDIT__AUTO_CLOSE_OLD_KEY=true` Telebuba tries at once and a background pass (`services/session_guard`) finishes it; off, that pass only logs `session_old_key_open` once a day per account.

A row can end in a terminal `problem` (`account_rekeys.problem`) instead of a retry: `old_key_unknown` (a row an earlier build stored with the old hash `0` that could not be resolved to exactly one session: not ours, not current, created before the re-key and last active within the day before it up to 5 minutes after) and `old_key_is_ours` (the close refused the stored hash as one of our own). Telebuba stops retrying, logs a warning, the card asks the operator to close the old session by hand, and a new re-key is refused (`rekey_needs_attention`) because the old key is still alive. A flood wait on the read is honoured for the next try.

One device: the account's primary session. A second sign-in of its own has its own key and is left alone. The account must have a proxy and be free of other features (warming, campaigns) while its client is swapped.

### An interrupted re-key (and other flows that make a key)

A crash in the middle of a re-key used to leave a scratch `<name>_rekey.session` and/or a `.rekey-aside` file that made every retry answer `rekey_session_conflict`, and could lose the old hash. Every flow that creates a NEW auth key (re-key, second device, a code/QR/passkey sign-in with the new API) now writes an intent first (`account_key_intents`, migration 122) and closes it when everything the key needs is recorded; only hashes, a sha256 mark of the account file's key and the device fingerprint are kept. The re-key advances it at acceptance of the login token (from then on a logout of the new client is owed, even if waiting for the login update fails), when the old hash is known and when the swap landed; the service closes it after storing the `account_rekeys` row. An undo whose logout is not confirmed keeps the scratch file and leaves the intent open. Every Telethon call of the re-key has a deadline.

`services.accounts._key_repair.repair_key_intents` settles open intents (every guard pass, and at the start of a re-key or a second-device retry; an account whose auth lock is held is a live flow and is skipped). Re-key: if the account file's key mark differs from the one recorded, the swap landed, so the old hash is stored (never auto-closed), the side copy goes to the quarantine and the scratch is removed; otherwise the scratch file is logged out by itself (`end_leftover_session`) and removed only on proof. A leftover scratch from before the journal is settled the same way at the top of a re-key. Second device: recorded means done, else the leftover file is logged out. Sign-in: the API a key was last connected with stays. Warnings: `session_rekey_recovered`, `session_rekey_interrupted`, `second_device_interrupted`, `sign_in_api_recovered`, `session_leftover_authorization` (an authorization with no file: it shows as a foreign session, close it by hand), `flow_intent_unresolved`, `flow_intent_repair_failed`.

### What the Telegram docs say about the two open questions

Verified against the pages on 2026-11-02, not assumed:

- **Can the new session end the old one at once?** The docs only give the rule in the error: `FRESH_RESET_AUTHORISATION_FORBIDDEN` — "You can't logout other sessions if less than 24 hours have passed since you logged on the current session" ([account.resetAuthorization](https://core.telegram.org/method/account.resetAuthorization)). Nothing says that a session created by `auth.acceptLoginToken` ([method](https://core.telegram.org/method/auth.acceptLoginToken), [QR login](https://core.telegram.org/api/qr-login)) is exempt or confirmed ahead of that. So the implementation tries at once and, if refused, schedules the retry from the answer; both outcomes are handled and tested, and which one happens is for the first live run to show.
- **2FA interplay.** Neither method page, nor the QR login page, nor [api/auth](https://core.telegram.org/api/auth) says what a token login does for an account with a cloud password (`Authorization.password_pending` exists but is unexplained). The implementation follows Telethon's flow: the second `auth.exportLoginToken` raises `SessionPasswordNeededError`, and `sign_in(password=...)` finishes it.
- **Unconfirmed.** `Authorization.unconfirmed` and `account.changeAuthorizationSettings(confirmed)` are documented ([api/auth](https://core.telegram.org/api/auth), login confirmation); what an unconfirmed session may not do is not.

**Not exercised against Telegram.** Only fakes and a fake file system run in the tests. A live run on one throwaway account must show: the token login works through the account's proxy with its stored fingerprint, the cloud-password finish, whether the new session may end the old one at once, and that Telegram's active-sessions list then shows only the new device.

## The watch: continuous, cheap, paced

`services/session_guard` runs one background task (started in the lifespan beside the survival probes, stopped before the client pool; one uvicorn worker). Every pass (`SESSION_AUDIT__GUARD_INTERVAL_SECONDS`, 5 min) it ends old re-key authorizations that are due (only with `SESSION_AUDIT__AUTO_CLOSE_OLD_KEY` on; off, it reminds) and re-audits **at most one** account. Each step has a deadline (`SESSION_AUDIT__GUARD_STEP_TIMEOUT_SECONDS`, 30 min) and a failure of any kind, a stray `CancelledError` and a timeout included, is logged as `session_guard_failed` while the loop goes on; only cancelling the task itself (shutdown) stops it.

- Which accounts: alive, behind a proxy, and not held by another feature (warming, campaigns, a channel-search loan). The first pass waits after startup (`WATCH_STARTUP_DELAY_SECONDS`) so a restart does not read the fleet at once.
- When: each account about every 6 to 12 hours (`WATCH_MIN_HOURS` / `WATCH_MAX_HOURS`). The interval is drawn afresh per account from a clipped log-normal in the service (core holds no randomness), so a fleet imported together never reads in step. An account never audited is due at once; one audited before a restart is due one drawn interval after that audit. A refused read is retried after `WATCH_RETRY_HOURS`.
- Proxies: no two accounts behind the same proxy within `WATCH_PROXY_SPACING_SECONDS`.
- A refusal that means the session is gone (`session_dead`, `account_deactivated`, `account_frozen`) goes through the normal session check, which records the status and journals `session_dead` together with the last audit before it, so the death is bracketed.
- An account whose auth lock is held (a sign-in in flight) is not read: the pass counts it as a refused read and tries again after `WATCH_RETRY_HOURS`.
- A **new** foreign session (one the previous audit did not list) is journalled (`foreign_sessions_found`), logged (`session_audit_foreign_found`), sent to the operator bot (the existing notification channel, kind `foreign_session`) and shown live: the accounts list's badge and an open Sessions card refresh from the log stream.
- If the account has a stored passkey, the watch asks Telegram whether it still lists it (`check_account_passkey`, read-only). A passkey that is gone is logged (`session_watch_passkey_missing`) and sent to the operator bot (kind `passkey_missing`): somebody else was in the account's security settings.

Switch it off with `SESSION_AUDIT__WATCH_ENABLED=false`; the old-key closing keeps running.

Copies of every session file and the quarantine for removed ones: `docs/session-vault.md`.

Which Telegram API (app title) each session uses, and the new neutral one: `docs/neutral-api.md`.

## A dead key is never silent

On 2026-11-14 an account's key died and was found 41 hours later, and the guard itself had stopped in the same moment. Four things now stand against that:

- **No stray cancellation.** When a client's update loop meets a dead key, Telethon disconnects it and cancels every request still waiting (`future.cancel()`). The client every flow builds (`core/telegram_client/_guarded_client.py`) turns that into the auth error Telethon recorded, or a `ConnectionError`, so callers classify it like any other refusal and no loop is ended by a `CancelledError` it never asked for.
- **The death watch** (`services/session_death_watch.py`, started with the guard) reads the live log bus. A row saying an account's key is dead (an action's `*_failed` with `error_type` `session_dead` / `account_deactivated`, or a refused audit) starts one ordinary session check for that account, at most once per `SESSION_AUDIT__DEATH_CHECK_COOLDOWN_SECONDS`. Busy accounts (warming, campaigns), which the watch never reads, are covered this way. Never for an account without a proxy.
- **A dead key is `unauthorized`**, whichever client found it, so it is journalled (`session_dead`) and the journal row tells the operator bot (`account_session_dead`, kind `session_dead`).
- **The watchdog** looks at the guard's heartbeat every guard interval: a guard whose task ended, or that did nothing for longer than a step's deadline plus two passes, is logged once as `session_guard_stalled` (to the bot, kind `session_guard`) and an ended one is started again. `GET /session-guard` serves the heartbeat; Settings shows it.

In the background pass each account's old-key close has its own deadline (`SESSION_AUDIT__OLD_KEY_ACCOUNT_TIMEOUT_SECONDS`): one stuck account is tried again later instead of holding the others.

## Key state and link state

`accounts.status` is the state of the KEY. The authorization probe is `probe_authorized` (`GetState`, only a 401 means "not signed in"; Telethon's `is_user_authorized()` answered `False` for a flood wait too). A session check that could not reach Telegram (`flood_wait`, `network_error`, `proxy_error`, `unknown_error`) leaves `status` as it was and writes `link_status` and `link_checked_at` instead, so a proxy hiccup never drops a live account from the guard, warming or mass tagging. Any real verdict (alive, unauthorized, frozen, ...) writes `status` and clears `link_status`. A legacy row that still holds a transport value in `status` keeps it until the next real verdict.

The guard's `recheck` step asks one such account per pass again (behind a proxy, not lent, its proxy not read within `SESSION_AUDIT__WATCH_PROXY_SPACING_SECONDS`): first after `SESSION_AUDIT__RECHECK_FIRST_MINUTES` (15), doubling per failed attempt up to `SESSION_AUDIT__RECHECK_MAX_HOURS` (6). A restored link is logged as `account_link_restored`. `session_error` (cannot be probed: API not configured) is not "the key is gone": it does not allow a login with a new API id nor a QR sign-in over the file.

## The guard sees more

- **Busy accounts are audited too.** An account another feature holds (warming, campaigns) is re-read by the watch once its last audit is older than `SESSION_AUDIT__WATCH_BUSY_HOURS` (24): one `account.getAuthorizations` through the pooled client, the owner keeps the account. An account never audited stays the owner's to start, and an account lent to another machine is never read.
- **Security settings** (`services/session_guard/_security_watch.py`, after each answered audit): the cloud-password status is compared with the last snapshot (`account_security_snapshots`: booleans and the reset date, never the e-mail pattern). `twofa_reset_pending` (WARNING) when a password reset is pending that the snapshot did not have, also on the first read: in seven days the password is removed. `security_settings_changed` (WARNING, `extra.changed`: field names among `has_password`, `has_recovery`, `email_unconfirmed`) when one of them differs, never on the first read. Telebuba's own set / change / remove / recovery e-mail changes forget the snapshot, so the next pass re-baselines.
- **Login codes nobody asked for.** The inbox classifies a message from Telegram's service user (777000) in the gateway; the text never leaves it. A login code while Telebuba expects none for the account (`services/accounts/_expected_codes.py`: opened by second-device / emulator code requests and the phone-code login, or a running sign-in holding the account's auth lock) is `login_code_unrequested` (WARNING); any other 777000 message is `telegram_service_message` (INFO). The code is never logged, stored or passed on.
- **Proxies** (`_proxy_watch`): one proxy bound to an account per guard pass is checked every `SESSION_AUDIT__PROXY_WATCH_HOURS` (6, 0 = off, plus up to 10 % jitter). `proxy_check_failed` (WARNING) when it became `failed`; `proxy_exit_changed` with `what: country` (WARNING) or `what: ip` (INFO, rotating proxies do that). Counts only, never an address. The guard also stops phone pods that are not on their account's proxy (`pods_off_proxy`).
- **Start-up bursts**: inbox listeners behind one proxy start one at a time with a random 1 to 3 s gap, and each health monitor's interval carries ±20 % jitter.
