# Масстегинг — план реализации по макету D

Источник истины по виду и поведению — макет D. Его файлы:
- `ui/VariantD.tsx` — страница;
- `ui/SettingsDialogD.tsx` — окно настроек и окно «Темп»;
- `ui/campaigns.ts` — состояния, доска, конвейер, журнал;
- `ui/model.ts` — черновик настроек и расчёты.

Открывается на `/prototype/masstagging?variant=D` (dev-сервер, `npm run dev`).
Исследование конкурентов: `RESEARCH.md`. Решения по прототипу: `NOTES.md`.

Образец среза — «Рассылка по чатам» (`chat_broadcast`). Тот же каркас на бэкенде и фронте: кампании, настройки с оптимистичной блокировкой, доска по целям, журнал. Где рассылка и масстегинг совпадают по смыслу, повторяем её решения, а не изобретаем свои.

## 0. Правила работы (обязательно)

- **Перед началом** прочитать `AGENTS.md` и `CODING_STANDARDS.md`. Затем `.mex/ROUTER.md` и маршруты:
  - `context/architecture.md`, `context/conventions.md`, `context/frontend.md`, `context/runtime-chat-broadcast.md`, `context/runtime-telegram.md`;
  - паттерны `add-service.md`, `add-telegram-task.md`, `add-api-endpoint.md`, `add-frontend-slice.md`, `add-log-event.md`.
- **Слои:** `api → services → core`, внешний I/O только в `core/`. Границы между слоями — типизированные Pydantic-модели.
- **Секреты:** никогда не печатать, не логировать и не коммитить сессии, tdata, JWT, данные прокси и ключи.
- **Живое приложение на :8080 не трогать:** не перезапускать, не логиниться, не слать в него запросы с записью. Тесты гонять только на фейках, никаких реальных аккаунтов Telegram.
- **Тесты:** у каждого изменения поведения есть тест. Тестовый файл — не больше 700 строк. Python-файл кода — не больше примерно 440 строк (гейт `aislop` предупреждает с 441); больше — значит выносить в модуль.
- **Отчёт:** писать только о проверках, которые реально запускались.
- **Git:** работать в своей ветке. Не делать force-push в `main`, не мержить PR самому, не включать auto-merge. Хуки не отключать (`--no-verify` нельзя).

## 1. Что строим (продуктовые решения уже приняты)

Новая страница «Масстегинг» в навигации, после «Рассылки». Два режима кампании:

| Режим | Что делает аккаунт | Что видит человек |
|---|---|---|
| **Отметки в сторис** | Публикует сторис из медиа кампании, в подписи @отмечает N людей. По умолчанию перед этим «создаёт диалог»: в личке с человеком включает автоудаление на 1 день и сразу выключает. | Пуш «X отметил(а) вас в истории» |
| **Прайминг** | Ничего не публикует и не пишет. Только включает и выключает автоудаление в личке. | Служебные строки «X включил(а) автоудаление» → идёт смотреть профиль, где лежит креатив |

### Раскладка страницы (как в D)

- **Сайдбар.**
  - Карточка «Кампании». У каждой кампании `SelectableCard`: название, строка «Сторис · 30 целей», плашка статуса. Слой действий: пуск/пауза, настройки, удаление.
  - Кнопка «+ Новая кампания»: создаёт кампанию и сразу открывает её настройки.
  - `HowItWorksCard`, по умолчанию свёрнута.
- **Основная колонка.**
  - **`PipelineCard` «Конвейер — {название}».**
    - Этапы: Аккаунты → Цели → [Диалог] → Сторис → Готово. В прайминге: Аккаунты → Цели → Автоудаление → Готово.
    - Строка-уведомление о том, что происходит, и плитки: «Отмечено X из Y», «Осталось», «Ошибок», «В сутки · ещё ≈N дн.».
    - Полоса прогресса — только после старта.
    - Строка с плашкой режима, «без Premium: N» с «?» и кнопкой «Настройки».
  - **Доска «Цели»** (`CollapsibleCard` + `DataTable`).
    - Вкладки «В работе · N» и «Готово · N», шестерёнка открывает окно «Темп».
    - Колонки: Кто, Когда, Аккаунт, Статус с короткой причиной, раскрытие.
    - Раскрытая строка: история цели и действия по состоянию.
  - `LogTerminal` «Журнал».

### Состояния кампании

Все обязательны и все видны в макете (кликайте по кампаниям в сайдбаре):

| Статус | Плашка | Кнопка конвейера | Уведомление | Доска |
|---|---|---|---|---|
| `draft` | Черновик | «Начать» (неактивна) | «Чтобы начать: …» — список нехватки | Пустая: «Здесь появятся люди из списка» + «Добавить» |
| `ready` | Готова | «Начать» | «Всё готово — можно начинать» | Все в очереди, «Когда» = — |
| `running` | Идёт | «Пауза» | «Идёт · следующая сторис через 2 мин» | Смешанные статусы |
| `paused` | Пауза | «Продолжить» | «На паузе · отмечено X из Y» | Без «Сейчас» и «Ждёт аккаунт» |
| `resting` | До завтра | «Пауза» | «Лимит на сегодня выбран · продолжим завтра в 09:00» | Вместо одинаковых строк одна фраза + «Показать список» |
| `done` | Готово | «Запустить снова» | «Готово · отмечено X из Y» | Сразу вкладка «Готово» |
| `failed` | Остановлена | «Продолжить» | Красное: «у всех аккаунтов флуд-лимит…» | Часть целей «Ждёт аккаунт» |

`draft` и `ready` сервер выводит из настроек, не хранит. «Запустить снова» начинает новый прогон. Пауза, остановка и отдых продолжают тот же прогон (как у рассылки).

### Статусы цели

| Статус | Значение |
|---|---|
| В очереди | Ещё не трогали |
| Диалог создан | Автоудаление сделано, ждёт ближайшую сторис |
| Сейчас | Аккаунт работает с ней прямо сейчас |
| Отмечен | Отмечена в сторис (или в прайминге — автоудаление сделано) |
| Ждёт аккаунт | Аккаунт поймал флуд-лимит |
| Пропущен | С причиной: «уже отмечен», «нет такого username» |
| Ошибка | С причиной: «закрыт приватностью» |

Действия в раскрытой строке:
- для «В очереди», «Диалог создан», «Ждёт аккаунт»: «Отметить сейчас» (в прайминге «Сейчас») и «Пропустить»;
- для «Ошибка» и «Пропущен»: «Вернуть в очередь».

### Окно настроек

`Modal size="form"`, шапка с названием и плашкой «Не сохранено», нумерованные разделы:

1. **Режим** — две outline-карточки, в каждой только название и одна строка.
2. **Аккаунты** — полоса аватарок, «+» открывает общий `BulkAccountPicker`. Аккаунты со спамблоком остаются в списке, но бледные. У заголовка плашки «без Premium: N» и «спамблок: N».
3. **Кого отмечать**
   - Переключатель «Свой список / Контакты аккаунтов».
   - Поле ввода, кнопки «Добавить N» и «Из файла», затем «Очистить».
   - Чипы: первые 8 и «ещё N».
   - Нужен третий источник — «База парсера», выбор сохранённой базы из модуля user parser (`services/user_parser`). Скопировать её при выборе, как рассылка копирует категории чатов. В макете его нет: добавить третьим сегментом.
4. **Сторис** (только для режима сторис)
   - Медиа (drop-зона, несколько файлов — по кругу).
   - Подпись со счётчиком 200 символов.
   - «Ссылка» с плашкой Premium. «Текст на кнопке» показывается, только если ссылка заполнена.
   - «Кто видит» (Все/Контакты), «Сколько висит» (6/12/24/48 ч), «Сначала создать диалог».
5. **Темп**
   - Для сторис: «Отметок в одной сторис», «Сторис в сутки», «Пауза между сторис». Для прайминга: «Людей в сутки», «Пауза между людьми».
   - «Мягкий старт», «Пропускать уже отмеченных», «Остановиться через N отметок/минут».
   - Свёрнутый блок «Защита от блокировок»: «Пауза при флуд-лимите», «Стоп после флуд-лимитов».

Внизу «Отмена» и «Сохранить». Сохранение запрещено, пока прогон идёт или отдыхает: тогда в окне уведомление «Кампания идёт. Поставьте на паузу, чтобы менять настройки». Окно «Темп» с доски меняет только темп и разрешено на ходу.

### Подсказки

Все пояснения только за `HelpHint` («?»): одна фраза + `example`. Тексты брать из `SettingsDialogD.tsx` дословно, затем в i18n. Никаких абзацев и `Notice` с пояснениями на странице и в окне. Исключение — уведомления о состоянии: «Кампания идёт…», «Чтобы начать: …».

## 2. Доменные правила и значения по умолчанию

| Параметр | По умолчанию | Откуда |
|---|---|---|
| Отметок в одной сторис | 5 (макс. 10) | GramGPT, «лучше не превышать 5» |
| Сторис в сутки (Premium) | 15, потолок 100 | лимит Telegram |
| Сторис в сутки (без Premium) | 1 — **жёсткий** потолок, поле на него не влияет | см. «проверить» ниже |
| Пауза между сторис | 1–2 мин | макет |
| Людей в сутки (прайминг) | 6 | GramGPT: 5–6 на старте, до 35–40 потом |
| Пауза между людьми | 20–60 с | GramGPT |
| Мягкий старт | вкл: дни 1–3 — 5–6 в сутки, пауза 200–600 с | GramGPT |
| Пауза при флуд-лимите | 500 с (и не меньше `FloodWait.seconds`) | GramGPT |
| Стоп после флуд-лимитов | 3 подряд → аккаунт отдыхает до завтра | GramGPT |
| Сначала создать диалог | вкл | TgNinja: без диалога пуш может не прийти |
| Кто видит сторис | Все | TgNinja |
| Сколько висит | 48 ч; без Premium всегда 24 ч | Telegram |
| Подпись | до 200 символов без Premium, до 2048 с Premium | Telegram |
| Ссылка-кнопка | только Premium | Telegram |
| Пропускать уже отмеченных | вкл — глобальный реестр по всем кампаниям | макет |
| Остановиться через | 50 отметок на аккаунт за запуск, 0 = без ограничения | макет |
| Резолв username | не больше 200 в сутки на аккаунт; счётчик обязателен | Telegram |
| Начало суток | 09:00 по местному времени сервера, константа | макет |

### Аккаунты в работу не берутся, если

- спамблок (`AccountRead.spam_status == 'limited'`): сторис публикуется, но пуши не доходят (TgNinja);
- аккаунт занят другой функцией: общий busy-lock, как у рассылки и нейрошиллинга. Показать на доске, кто его держит, отказ не нужен;
- статус аккаунта не `alive`.

Если ни одного рабочего аккаунта нет, прогон уходит в `failed`. Если у всех рабочих аккаунтов выбран дневной лимит, прогон уходит в `resting`.

### Ошибки Telegram → статус цели

Точные имена исключений сверить по исходникам Telethon в `.venv`.

| Ошибка | Что делаем |
|---|---|
| `FloodWaitError` | Аккаунт на паузе `max(500, seconds)`, цель — «Ждёт аккаунт»; после 3 подряд аккаунт отдыхает до завтра |
| `PeerFloodError` | Помечаем спамблок, аккаунт выходит из прогона |
| `UserPrivacyRestrictedError` (и родственные приватности) | Цель «Ошибка: закрыт приватностью» |
| `UsernameNotOccupiedError`, `UsernameInvalidError` | «Пропущен: нет такого username» |
| Лимит сторис (`StoriesTooMuch` и т. п.) | Аккаунт отдыхает до завтра |
| `PremiumAccountRequired` | У аккаунта выключается ссылка / срок жизни, повтор без них |

### Проверить на тестовом аккаунте до мержа

Это делает оператор, не агент. Решения в коде должны легко меняться константой, а в PR надо явно написать «проверить вручную».

- Сколько сторис в сутки реально даёт аккаунт без Premium (источники говорят 1, 3 и «меньше»).
- Нужен ли «диалог» для пуша об отметке.

Копировать структуру `chat_broadcast`, имена — `masstagging`.

### 3.1 `core/telegram_client` — действия Telegram

Паттерн `add-telegram-task.md`, действия в `schemas/telegram_actions.py`.

1. **`ToggleHistoryTtl` (прайминг / «диалог»).**
   - Резолв пира (username или телефон).
   - `messages.SetHistoryTTLRequest(peer, period=86400)`, короткая случайная пауза 1–3 с, затем `period=0`.
   - Вернуть типизированный результат: ok или ошибка из таблицы выше.
   - Телефон без контакта не резолвится: либо `contacts.ImportContacts` с последующим удалением контакта, либо такие цели — «Пропущен: телефон не найден». **Выбрать второе, проще и безопаснее**, и сказать об этом в PR.
2. **Расширить `PostStory`** в `_media_stories.py`, обратно совместимо:
   - упоминания: список резолвленных пользователей → в подпись дописываются `@username`, plus сущности `InputMessageEntityMentionName`, если `@username` нет;
   - ссылка: `MediaAreaUrl` с позицией по умолчанию (только если у аккаунта Premium);
   - `privacy_preset` «all» уже есть, проверить;
   - срок жизни `period_seconds`, без Premium принудительно 86400.
   Тесты на сборку запроса — без сети, на фейковом клиенте, как существующие тесты сторис.
3. **Резолв username** с дневным счётчиком (200 в сутки на аккаунт), кешируется в целях кампании, чтобы не резолвить повторно.
4. **Проверка спамблока:** переиспользовать `_spam.py` и `spam_status` аккаунта, нового запроса не делать.

### 3.2 `schemas/masstagging*.py`

- `MasstaggingMode`, `CampaignStatus`, `TargetState`, `TargetReason` — `Literal` или `StrEnum`.
- `MasstaggingSettings`: все поля окна настроек с границами (`Field(ge=…, le=…)`), значения по умолчанию из раздела 2. В Pydantic проверяется `min ≤ max` у диапазонов.
- `MasstaggingCampaign` (строка сайдбара): id, name, mode, status, target_count, account_count.
- `MasstaggingBoard`: campaign, counters (tagged, left, failed, per_day, days_left), rows. У каждой строки: target, state, reason, when (ISO или null), account_id, history[].
- `MasstaggingSettingsRead/Write`: `updated_at` для оптимистичной блокировки (`expected_updated_at`), как у рассылки.
- Запросы действий по цели: `now | skip | requeue`.

### 3.4 `services/masstagging/`

Структура по образцу `services/chat_broadcast`, каждый файл до ~440 строк:
- `campaigns.py`: CRUD, вывод `draft`/`ready` из настроек (список нехватки — те же строки, что в макете).
- `targets.py`:
  - разбор ввода: `@user`, `user`, `t.me/user`, `+7…`; `t.me/chat` → участники через user parser;
  - дедупликация;
  - импорт из файла;
  - источники «контакты аккаунтов» и «база парсера».
- `pace.py`: дневные лимиты с учётом Premium, мягкого старта и счётчиков. Возвращает «можно ли сейчас» и «когда в следующий раз».
- `_coordinator.py` + `_worker.py`: одна asyncio-задача на аккаунт, как у прогрева и рассылки.
  - **Сторис-режим, на аккаунт:** взять до N следующих целей. Если `primeFirst`, для каждой `ToggleHistoryTtl` → «Диалог создан». Затем одна сторис с упоминанием всех успешных → «Отмечен». Затем пауза между сторис.
  - **Прайминг:** цель → `ToggleHistoryTtl` → «Отмечен», пауза между людьми.
  - Медиа берётся по кругу.
  - Флуд-логика, спамблок, отдых до завтра — по разделу 2.
  - Все рабочие аккаунты на отдыхе → `resting` + `rest_until`. Ни одного рабочего → `failed`.
  - Список закончился → `done`.
- Busy-lock через общий механизм владения аккаунтом, как у рассылки (его тест — `tests/services/test_account_owner_chat_broadcast.py`).
- `board.py`: сборка `MasstaggingBoard`. Порядок строк задаёт фронт, как у рассылки.
- `actions.py`: now/skip/requeue с проверкой состояния.
- Журнал: все события через `log_event` с кодами `masstagging_*` (паттерн `add-log-event.md`):
  - `masstagging_dialog_created`, `masstagging_story_posted`, `masstagging_target_tagged`;
  - `masstagging_target_failed`, `masstagging_target_skipped`;
  - `masstagging_flood_pause`, `masstagging_account_rested`, `masstagging_spamblock`;
  - `masstagging_run_started`, `masstagging_run_paused`, `masstagging_run_resting`, `masstagging_run_done`, `masstagging_run_failed`.
  - Обязательно `extra` с target и причиной, без секретов.
- Перезапуск сервера: прогон в `running` после рестарта продолжается или помечается так же, как это делает рассылка (`_runtime.py`). Повторить поведение, с тестом.

## 7. Сдача: проверки → ревью → PR → боты → зелёный CI

1. **Локально, все команды из `.mex/context/setup.md`:**
   - `uv run ruff check . && uv run ruff format --check . && uv run ty check .`
   - `uv run pytest`: вывод писать в файл, судить по exit code.
   - `uv run pre-commit run --all-files`, pre-push хуки `arch-guard` и `aislop`.
   - `uv run python -m tools.gen_api`: дифф должен быть закоммичен.
   - `cd frontend && npm ci && npm run gates && npm run build`.
   - MEX check.
2. **Самопроверка:** запустить `/code-review high` на ветке. Исправить всё подтверждённое, повторять, пока чисто.
3. **Коммиты** — логическими кусками (core, services, api, frontend, удаление прототипа, mex), сообщения на английском, с атрибуцией из системных инструкций.
4. **PR:** `git push -u origin <ветка>`, `gh pr create` в `main`. Заголовок «Add masstagging: story mentions and priming». В описании:
   - что сделано;
   - скриншоты-ссылки не нужны;
   - раздел **«Проверить вручную на тестовом аккаунте»** — оба пункта из раздела 2;
   - список выполненных проверок.
5. **Привязать PR** к сессии (`ccd_pr` tools: `get_status`/`bind_pr`).
6. **Боты.** Дождаться ревью **CodeRabbit** и **Macroscope**, читать через `gh pr view --comments` и `gh api repos/{owner}/{repo}/pulls/{n}/comments`.
   - Каждое замечание: исправить, или ответить в треде, почему не исправляем (только если замечание неверно).
   - Закрыть треды.
   - Повторять, пока боты не перестанут находить новое.
7. **CI:** все джобы `ci.yml` и `mex.yml` зелёные. Красное — разобрать лог (`gh run view --log-failed`), чинить причину, без обхода проверок. Не ставить `skip` и не ослаблять гейты.
8. **Не мержить.** В конце отчитаться:
   - ссылка на PR;
   - что сделано;
   - какие проверки реально прошли;
   - что осталось оператору (ручная проверка из раздела 2, визуальная проверка страницы).
